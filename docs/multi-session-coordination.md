# 複数セッション（Mac / ワーカー機 / HPC）の協調

## 情報の置き場
- **進捗ボード** `docs/STATUS.md`（HPC が自動更新、環境ごとの現状と依頼）と **追跡 issue**（時刻付きコメント、依頼・結果・提出の告知）。会話履歴ではなくファイルで現在地を判断する。
- 依頼は `docs/<env>/REQUEST_<date>.md` に「データ・形式・納期・コミット接頭辞」を書く。納品は同じディレクトリに。

## git の作法
- push 前に必ず `git fetch && git rebase --autostash origin/main`。他セッションの未コミット差分（untracked 含む）は**絶対に add しない**（`git add <明示したパス>` のみ）。
- 自動追記ファイル（seed 台帳、ログ）は**セッション／マシンごとに分ける**。共有ファイルへの自動追記は rebase 競合を毎回起こす。
- ワーカー機は別クローン（`~/<repo>_sweep`）で pull 専用にし、生成物は `git clean` できる場所に置く。pull が untracked で止まる前提で運用する。
- コミット接頭辞で出所を示す（`mac:`、`intel:`、HPC は exp 番号）。

## 提出
- 提出は**必ずユーザー承認**。提出前に有効ペア（最新 2 本）を API で確認し、何が退役するかを明記する。別マシンが直前に提出していないかも確認。
- 候補の独立確認は別環境で（同 seed・両席・相手セット・W→L / L→W・エラー・最大手時間）。staged 版と提出版の sha を照合する（別物を確認してしまった実例あり）。

## 分業
- 土台ごとに担当を分ける（例: HPC はテープの上、Mac は自作 planner の上）。重複を避け、互いの結果は issue で照合。
- 外部レビュー（Codex 等）は毎日 3 観点（実装監査・評価・研究案）+ 1 往復の議論。上限時は別 LLM の独立エージェントで代替。仮説を伝えない**独立セッション複数に同じ生データ**を渡す手法が最終日の発見を生んだ。
